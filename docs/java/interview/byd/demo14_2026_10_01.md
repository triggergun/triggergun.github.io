# 异构系统集成：企业服务总线与 API 网关设计方案

## 一、建设背景与目标

大型制造企业通常同时运行 ERP、MES、WMS、CRM、SRM、PLM、OA、财务系统以及设备管理平台等业务系统。这些系统可能由不同厂商建设，采用不同技术栈、数据模型、接口协议和身份认证方式。

如果系统之间直接互相调用，会逐渐形成大量点对点依赖：一个系统接口变化，多个调用方都要修改；同一业务数据在多个系统重复维护；接口权限、日志和异常处理分散在各系统中；跨系统业务流程难以追踪。

建设企业集成平台的核心目标是：

- **系统解耦**：业务系统不再彼此深度依赖，通过统一集成能力交换数据和调用服务。
- **数据互通**：建立统一的数据交换标准、主数据管理和数据同步机制。
- **统一认证授权**：统一身份认证、服务身份、访问控制和权限审计。
- **可靠集成**：支持消息持久化、重试、幂等、补偿、死信处理和故障隔离。
- **可观测与可治理**：统一管理接口、消息、调用链、告警、版本和数据质量。
- **渐进式改造**：尽量复用现有系统能力，通过适配器接入，不要求一次性重构所有系统。

需要明确：企业服务总线（ESB）与 API 网关不是同一种组件。API 网关主要处理同步 API 流量的统一入口、认证、路由和治理；ESB 或消息集成平台主要处理系统间协议适配、消息路由、异步通信和流程编排。现代架构通常采用二者协同，而不是只部署其中一个。

## 二、总体架构设计

建议采用“API 网关 + 消息集成平台 + 集成适配器 + 主数据与治理平台”的分层架构。

```text
                         内部员工 / 合作伙伴 / 移动端
                                      |
                             统一身份认证中心
                         OAuth 2.0 / OIDC / SSO
                                      |
                              WAF / API 网关
                    认证、鉴权、限流、路由、审计、版本
                                      |
                    +-----------------+-----------------+
                    |                 |                 |
                API 服务          集成服务          开放 API
                    |                 |                 |
                    +-----------------+-----------------+
                                      |
                          集成与消息交换平台
                 +--------------------+--------------------+
                 |                    |                    |
              消息队列             事件总线             流程编排
          Kafka/RabbitMQ       Kafka/Pulsar          工作流引擎
                 |                    |                    |
                 +--------------------+--------------------+
                                      |
                              协议与系统适配层
              +-----------+-----------+-----------+-----------+
              |           |           |           |           |
             ERP         MES         WMS         CRM         SRM
              |           |           |           |           |
              +-----------+-----------+-----------+-----------+
                                      |
                         数据治理与基础支撑平台
             主数据管理 / 数据目录 / 数据标准 / 元数据 / 质量
             配置中心 / 注册发现 / 密钥管理 / 监控告警 / 日志追踪
```

各层职责如下：

- **统一身份认证中心**：负责用户登录、单点登录、令牌签发、身份生命周期和多因素认证。
- **API 网关**：负责外部和内部 API 的统一接入、认证校验、路由、限流、协议转换、访问日志和防护。
- **集成服务层**：封装跨系统业务能力，避免调用方直接依赖各业务系统的内部接口。
- **消息与事件平台**：承载异步数据交换、业务事件通知、削峰填谷和系统间解耦。
- **协议与系统适配层**：屏蔽 ERP、MES、WMS 等系统在接口协议、字段和数据格式上的差异。
- **数据治理平台**：维护主数据、数据标准、数据质量、数据目录和数据血缘。
- **可观测与运维平台**：统一采集指标、日志、链路、告警和审计记录。

## 三、API 网关设计

API 网关是同步请求的统一入口。建议所有跨系统的同步 API 调用优先经过网关或内部服务入口，避免应用随意访问其他系统的地址。

API 网关应具备以下能力：

- **统一路由**：根据域名、路径、HTTP 方法、请求头或版本号，将请求转发到目标服务。
- **认证**：验证 OAuth 2.0 / OIDC 访问令牌，识别用户或调用服务的身份。
- **授权**：结合角色、权限、资源和数据范围判断是否允许访问。
- **限流与配额**：按用户、应用、租户、接口或 IP 设置访问频率和并发上限。
- **熔断与超时**：下游系统响应异常时及时失败，避免故障扩散。
- **协议转换**：在必要时处理 HTTP、HTTPS、WebSocket 等协议或格式转换。
- **版本管理**：支持 `/api/v1`、`/api/v2` 等版本并行运行和逐步下线。
- **审计与追踪**：记录调用主体、目标接口、结果、耗时、关联 ID 等信息。
- **安全防护**：结合 WAF、请求大小限制、参数校验、IP 策略和敏感信息保护。

网关不应承载复杂业务逻辑，也不宜把所有业务编排都写成网关插件。业务规则应放在领域服务或集成服务中，网关专注于流量治理和安全边界。

## 四、企业服务总线与消息平台设计

ESB 适合承担协议适配、消息路由、数据转换和部分流程编排。对于高吞吐、事件驱动和微服务场景，也可以使用消息代理与轻量集成服务组合实现，不必强制采用传统重量级 ESB。

推荐按通信方式划分：

- **同步请求**：适用于需要立即得到结果的查询或命令，例如查询库存、校验客户信息。
- **异步消息**：适用于订单创建、生产报工、库存变更、物流状态更新等不要求调用方立即等待的场景。
- **事件通知**：用于广播已发生的业务事实，例如 `OrderCreated`、`MaterialIssued`、`ProductionCompleted`。
- **批量数据交换**：适用于历史数据迁移、定时对账和大批量主数据同步，可采用文件交换、批处理或数据集成任务。

消息平台的关键设计包括：

- **消息持久化**：消息写入可靠存储，避免消费者短暂不可用导致数据丢失。
- **消费确认**：消费者完成业务处理后再确认消息，失败时按策略重试。
- **幂等处理**：为每条消息分配唯一事件 ID 或业务幂等键，防止重复消费造成重复扣库存、重复记账。
- **重试与死信队列**：短暂故障进行有限次数重试；超过阈值后进入死信队列，供人工或自动修复。
- **顺序保证**：只在业务确实要求顺序的范围内设计分区键和顺序消费，避免不必要地牺牲吞吐。
- **消息版本**：事件结构增加字段时保持向后兼容；破坏性变更应发布新版本。
- **消息追踪**：在消息头中传递 `trace_id`、`event_id`、`correlation_id`、`source_system` 和时间戳。

消息“至少一次投递”是常见可靠性策略，但这意味着消费者必须支持幂等。不要仅凭消息队列配置就宣称整个跨系统业务具备端到端“恰好一次”语义。

## 五、ERP、MES、WMS、CRM 的集成场景

系统集成应围绕业务事件和业务边界设计，而不是简单地把各系统数据库表互相同步。

典型业务场景如下：

| 业务场景 | 生产者 | 消费者 | 推荐方式 | 关键控制 |
|---|---|---|---|---|
| 销售订单转生产需求 | CRM/ERP | ERP/MES | API 命令 + 事件通知 | 订单号幂等、状态校验 |
| 生产工单下发 | ERP | MES | 消息或集成服务 | 工单版本、重复下发控制 |
| 物料配送请求 | MES | WMS | 消息或 API | 物料编码统一、数量单位校验 |
| 领料与退料 | WMS | ERP/MES | 业务事件 | 库存流水、事务对账 |
| 完工入库 | MES | WMS/ERP | 事件驱动 | 批次、数量、质量状态 |
| 库存查询 | ERP/MES/CRM | WMS | 同步 API 或缓存查询 | 超时、限流、数据时效 |
| 客户与供应商资料 | 主数据平台 | CRM/ERP/SRM | 主数据分发事件 | 主数据编码、变更审批 |
| 发货与物流状态 | WMS/物流平台 | CRM/ERP | 异步事件 | 运单号、状态流转校验 |

集成时要特别关注以下原则：

- **明确数据归属**：每类核心数据都要指定权威系统。例如库存实物账可能由 WMS 管理，财务库存价值由 ERP 管理，不能让多个系统同时成为同一字段的最终权威来源。
- **统一业务主键**：订单号、工单号、物料编码、客户编码、批次号等应有明确规则，并维护跨系统映射关系。
- **统一状态定义**：例如订单“已创建”“已审核”“已下发”“已完成”的含义和状态迁移必须统一。
- **避免数据库直连**：原则上通过 API、消息或受控数据交换访问业务数据。确有历史系统限制时，应使用隔离的只读同步或适配方案，并制定退出计划。
- **建立对账机制**：对订单数量、库存数量、完工数量、出入库流水等关键数据定期核对，发现差异后形成可追踪的异常工单。

## 六、统一认证与授权设计

统一认证的目标是让用户和系统使用可验证的身份访问资源，而不是让所有系统共享一个管理员账号或固定密码。

建议采用 OAuth 2.0 和 OpenID Connect（OIDC）：

- **OIDC**：解决用户身份认证和登录信息传递，适合企业单点登录。
- **OAuth 2.0**：解决客户端如何获得访问 API 的授权令牌。
- **JWT 或不透明令牌**：作为访问令牌的实现形式。JWT 便于本地验证，但必须严格校验签名、发行者、受众和有效期；不透明令牌通常需要向授权服务器或内省端点验证。
- **服务间认证**：系统调用系统时使用独立的服务身份，优先采用客户端凭证模式、私钥 JWT 或 mTLS 等机制，不使用员工个人令牌代替服务身份。
- **单点登录**：员工通过统一身份平台登录，再按权限访问 ERP、MES、WMS、CRM 等系统。

授权建议采用 RBAC 与 ABAC 组合：

- **RBAC（基于角色的访问控制）**：例如生产主管、仓库管理员、销售人员、财务人员。
- **ABAC（基于属性的访问控制）**：根据工厂、组织、业务单元、数据归属、环境、设备或风险等级进一步限制访问。
- **最小权限原则**：用户和服务只获得完成任务所需的最小权限。
- **资源级授权**：不能只判断用户是否能访问某个 API，还应判断其是否能访问指定工厂、订单、仓库或客户的数据。
- **令牌生命周期**：设置合理有效期、刷新策略、吊销机制和密钥轮换流程。
- **审计留痕**：记录身份、权限决策、资源、操作、时间和结果，敏感操作应支持审批或二次验证。

一个典型的 API 访问流程：

```text
用户登录企业身份平台
        |
        v
身份平台完成认证并签发令牌
        |
        v
客户端携带 Access Token 请求 API 网关
        |
        v
网关验证签名/有效期/发行者/受众
        |
        v
网关或授权服务检查接口权限
        |
        v
集成服务执行资源级和数据范围校验
        |
        v
调用目标系统并记录审计日志
        |
        v
返回结果
```

注意：网关完成身份和粗粒度权限校验，并不意味着业务服务可以省略资源级授权。对订单、库存、工资、客户等敏感数据，最终业务服务仍应执行必要的权限判断。

## 七、数据标准与主数据管理

异构系统最难的问题往往不是网络连接，而是数据含义不一致。例如 ERP 中的物料编码、MES 中的产品编码和 WMS 中的库存 SKU 可能存在不同命名、单位、分类和状态。

建议建立企业级数据标准：

- **主数据**：物料、产品、客户、供应商、组织、工厂、仓库、人员、设备等。
- **参考数据**：国家地区、计量单位、币种、产品类别、订单类型、状态码等。
- **交易数据**：订单、工单、领料单、入库单、出库单、发货单等。
- **元数据**：字段名称、类型、含义、责任部门、敏感级别、来源和更新频率。

主数据管理建议遵循：

- 为每类主数据指定唯一权威维护系统或主数据管理平台。
- 统一编码规则，避免不同系统各自生成无法映射的编码。
- 建立数据映射表，记录源系统编码、企业标准编码和目标系统编码。
- 通过审批、校验和变更事件发布主数据变更。
- 对关键字段建立质量规则，例如必填、唯一性、格式、有效范围和引用完整性。
- 记录数据版本、生效时间和变更来源，支持历史追溯。

不要把“数据互通”理解为所有系统数据库完全一致。更合理的目标是：关键数据有统一定义、明确权威来源、受控分发，并允许各系统保留适合自身业务的内部模型。

## 八、接口规范与数据交换标准

建议制定统一的接口和消息规范，并将其纳入开发与上线流程。

API 规范建议包括：

- 使用 HTTPS，优先采用 RESTful API；对确有需要的场景可使用 gRPC。
- 使用统一命名、资源路径、HTTP 状态码和错误码。
- 使用 OpenAPI 描述接口，接口文档与代码版本同步。
- 请求和响应包含统一的追踪标识。
- 对分页、排序、过滤、时间格式、时区和金额精度制定规范。
- 对敏感字段进行脱敏，避免在 URL、日志和错误信息中暴露密钥或个人信息。
- 对接口设置超时、限流、最大请求体和并发限制。

消息规范建议包括：

```json
{
  "event_id": "evt-20261114-000001",
  "event_type": "ProductionOrderReleased",
  "event_version": "1.0",
  "source_system": "ERP",
  "occurred_at": "2026-11-14T09:30:00+08:00",
  "trace_id": "trace-abc123",
  "business_key": "MO-20261114-001",
  "data": {
    "production_order_no": "MO-20261114-001",
    "material_code": "MAT-10001",
    "planned_quantity": 500,
    "unit": "PCS",
    "factory_code": "F01"
  }
}
```

字段含义：

- `event_id`：事件唯一标识，用于去重和追踪。
- `event_type`：事件类型，表示发生了什么业务事实。
- `event_version`：事件结构版本。
- `source_system`：事件来源系统。
- `occurred_at`：业务事件发生时间，建议携带时区。
- `trace_id`：跨系统链路追踪标识。
- `business_key`：业务对象的唯一标识。
- `data`：业务载荷，字段应遵循企业数据标准。

上述 JSON 仅为示例，生产环境还应制定字段类型、必填规则、兼容策略、敏感级别和 Schema 校验规则。

## 九、可靠性、事务与异常处理

跨系统调用无法简单依赖单个数据库事务保证整体一致性。应根据业务重要程度设计可靠性机制。

- **超时控制**：每个调用都应设置连接超时和读取超时，避免线程长期占用。
- **有限重试**：只对可恢复错误重试，采用指数退避和随机抖动；不要对所有错误无限重试。
- **幂等键**：对创建订单、扣减库存、入库等命令使用业务幂等键，确保重复请求不会重复产生副作用。
- **熔断隔离**：下游系统持续失败时暂停请求，避免故障扩散；恢复后按策略逐步放量。
- **补偿机制**：对跨系统长流程采用 Saga 或业务补偿。例如订单已创建但仓库预留失败，应执行取消预留或进入人工处理。
- **事务发件箱（Outbox）**：业务数据和待发布事件在同一数据库事务中写入，再由后台任务可靠发布，降低“业务提交成功但消息未发出”的风险。
- **对账与修复**：为关键流程建立定时对账、差异告警和人工修复入口。
- **死信管理**：死信消息要有原因、原始载荷、重试次数、处理状态和责任人，不能只堆积不处理。

## 十、部署与技术选型建议

技术选型应结合现有系统、团队能力、吞吐量、可用性要求和运维能力，不应仅追求技术栈数量。

| 能力 | 可选技术 | 适用说明 |
|---|---|---|
| API 网关 | Apache APISIX、Kong、Spring Cloud Gateway | 统一 API 接入、路由和治理 |
| 消息队列/事件流 | Apache Kafka、RabbitMQ、Pulsar | 异步消息、事件分发和削峰 |
| 传统 ESB / 集成 | Apache Camel、MuleSoft、企业现有 ESB | 协议适配、路由和复杂系统连接 |
| 身份认证 | Keycloak、企业 IAM、现有统一身份平台 | OIDC、OAuth 2.0、SSO |
| 服务治理 | Kubernetes、Consul 等 | 服务部署、发现和配置治理 |
| 流程编排 | Camunda、Flowable、Temporal | 长流程、审批和跨系统业务编排 |
| 可观测性 | Prometheus、Grafana、OpenTelemetry、ELK/OpenSearch | 指标、链路、日志和告警 |
| 数据治理 | MDM 平台、数据目录和数据质量平台 | 主数据、标准、质量和血缘 |

一种可落地的组合示例：

- API 网关：Apache APISIX 或 Kong。
- 消息平台：Kafka；若主要是传统任务队列和复杂路由，也可评估 RabbitMQ。
- 集成适配：Apache Camel 或 Spring Boot 集成服务。
- 认证中心：Keycloak 或企业已有 IAM。
- 流程编排：根据长流程复杂度选择 Camunda、Flowable 或 Temporal。
- 监控追踪：Prometheus + Grafana + OpenTelemetry + 日志平台。

如果企业已有成熟 ESB、IAM 或消息中间件，应优先评估复用与整合，避免重复建设。关键生产系统应部署在符合企业安全、网络分区、容灾和数据驻留要求的基础设施中。

## 十一、安全设计

企业集成平台连接多个核心系统，是重要的安全边界，应从网络、身份、数据和运维多个层面设计。

- **网络分区**：按办公区、生产区、DMZ、数据区划分网络边界，限制跨区访问。
- **传输加密**：外部和跨安全域通信使用 TLS；高安全场景采用双向 TLS。
- **密钥管理**：使用密钥管理系统或安全凭据库保存密钥、密码和证书，禁止写入代码仓库。
- **服务身份隔离**：每个系统或应用使用独立身份和凭据，支持吊销和轮换。
- **权限最小化**：网关、消息消费者、适配器和业务服务分别配置最小权限。
- **数据分级分类**：识别个人信息、商业机密、生产工艺和财务数据，按级别控制访问、存储和传输。
- **日志脱敏**：不得记录明文密码、访问令牌、私钥或不必要的敏感业务字段。
- **供应链安全**：对依赖组件、容器镜像和部署制品进行漏洞扫描与版本管理。
- **安全审计**：对权限变更、密钥操作、敏感数据访问和高风险业务操作保留审计记录。

## 十二、监控、告警与运维治理

集成平台上线后，必须能够回答“哪个系统调用了哪个接口、消息是否送达、失败在哪里、影响了哪些业务”。

建议建立统一监控指标：

- API：请求量、成功率、错误率、P95/P99 延迟、限流次数、超时次数。
- 消息：生产速率、消费速率、消费延迟、积压量、重试量、死信量。
- 适配器：连接状态、处理耗时、失败数、线程池和连接池使用率。
- 业务：订单同步成功率、工单下发时延、库存对账差异、完工入库成功率。
- 安全：认证失败、异常访问、权限拒绝、令牌异常和高风险操作。

运维管理还应包括：

- 接口目录和责任人登记。
- API 与消息 Schema 版本管理。
- 变更评审、灰度发布和回滚方案。
- 生产环境配置与密钥集中管理。
- 故障分级、值班响应和应急预案。
- 消息重放、死信处理和数据补偿的审批流程。
- 定期容量评估、灾备演练和恢复测试。

## 十三、实施路线图

建议分阶段建设，先解决高价值、高频率的集成问题，再逐步推广到全企业。

| 阶段 | 主要工作 | 交付成果 |
|---|---|---|
| 第一阶段：现状盘点 | 梳理系统、接口、数据归属、网络和认证方式 | 系统清单、接口清单、集成现状图 |
| 第二阶段：标准与底座 | 建立 API 规范、消息规范、身份规范和环境 | API 网关、身份认证、消息平台基础环境 |
| 第三阶段：试点集成 | 选择 ERP-MES 或 MES-WMS 等核心链路 | 适配器、事件模型、端到端追踪和对账 |
| 第四阶段：推广扩展 | 接入 CRM、SRM、PLM、财务等系统 | 企业级服务目录和消息主题目录 |
| 第五阶段：治理优化 | 完善主数据、数据质量、权限审计和 SLA | 数据治理机制、运营报表和持续改进流程 |

试点建议选择“ERP 下发生产工单到 MES，再由 MES 触发 WMS 物料配送”这样的端到端流程。它能够覆盖同步查询、异步事件、主数据映射、幂等、异常补偿和业务对账等关键能力。

每个阶段都应定义验收指标，例如接口成功率、消息端到端延迟、重复业务处理率、数据对账差异率、故障恢复时间和权限审计覆盖率。具体目标值应根据生产规模和业务 SLA 测算，不应直接套用未经验证的数字。

## 十四、关键设计决策与常见误区

**建议坚持的设计决策：**

- API 网关负责同步 API 流量治理，消息平台负责异步解耦，二者职责清晰。
- 集成服务负责跨系统业务适配，业务系统保留自身领域逻辑。
- 以业务事件和稳定契约连接系统，而不是让系统依赖彼此的数据库结构。
- 每类主数据明确权威来源，建立编码、状态和单位标准。
- 对关键命令实现幂等、重试、补偿和对账。
- 认证与授权分层实施，既检查调用者身份，也检查具体业务资源权限。
- 通过统一追踪标识贯穿网关、集成服务、消息和业务系统。

**需要避免的误区：**

- **只建 API 网关就认为完成系统集成**：网关不能代替消息可靠投递、数据转换和业务流程治理。
- **把 ESB 做成新的单体系统**：所有业务逻辑集中在总线会形成新的耦合和单点风险，应按领域拆分集成能力。
- **所有通信都使用同步 HTTP**：高峰期容易造成级联超时，适合异步的业务应采用消息或事件。
- **所有数据都实时双向同步**：容易形成数据冲突和循环更新，应先明确数据权威来源。
- **只做接口级授权**：忽略工厂、仓库、订单和客户等资源级数据权限。
- **认为消息队列天然保证业务不重复**：消费者仍需幂等，业务仍需对账。
- **忽略遗留系统限制**：老系统可能只有数据库、文件或专有协议接口，应通过隔离适配器渐进接入。
- **一次性替换所有系统**：风险和成本都很高，优先建立集成底座并分批迁移。

## 十五、总结

面向 ERP、MES、WMS、CRM 等数十个异构系统，推荐采用“API 网关 + 消息集成平台 + 适配器 + 统一身份认证 + 数据治理”的企业集成架构。

API 网关解决统一入口、认证鉴权和流量治理；消息平台解决异步解耦和可靠数据分发；适配器解决协议与数据模型差异；身份平台解决统一认证和服务身份；主数据与数据治理解决编码、口径和数据质量问题。

真正成功的企业集成平台，不是把所有系统简单连起来，而是建立一套稳定、可治理、可追踪、可演进的企业级集成标准。应从一个完整业务链路试点，验证可靠性、安全性和数据一致性，再逐步扩展到全企业。
